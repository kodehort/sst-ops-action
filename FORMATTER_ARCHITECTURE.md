# Formatter Architecture Documentation

## Overview

This document clarifies the architecture and responsibilities of the formatting system in the SST Operations Action. The system has two main formatters with distinct purposes.

## Formatter Components

### 1. OperationFormatter (`src/github/formatters.ts`)

**Purpose**: Formats operation results for GitHub integration (PR comments and workflow summaries)

**Responsibilities**:
- Generate markdown content for PR comments
- Generate markdown content for workflow summaries
- Format operation-specific content (deploy stats, diff changes, removal info)
- Create rich, human-readable output with emojis and badges

**Output Destinations**:
- GitHub Pull Request comments
- GitHub Actions workflow summaries
- Visual, markdown-formatted content

**Key Methods**:
```typescript
class OperationFormatter {
  formatOperationComment(result: BaseOperationResult): string
  formatOperationSummary(result: BaseOperationResult): string

  // Operation-specific formatters
  private formatDeployComment(result: DeployResult): string
  private formatDeploySummary(result: DeployResult): string
  private formatDiffComment(result: DiffResult): string
  private formatDiffSummary(result: DiffResult): string
  private formatRemoveComment(result: RemoveResult): string
  private formatRemoveSummary(result: RemoveResult): string
}
```

**Example Output** (PR Comment):
```markdown
## ✅ Deploy Success

**Stage**: production
**App**: my-sst-app

### 📊 Resources Changed: 5

- ✅ AWS::Lambda::Function my-function
- ✅ AWS::S3::Bucket my-bucket
- ⚡ AWS::DynamoDB::Table my-table

### 🔗 Links

- [SST Console](https://console.sst.dev/...)

---
Generated by SST Operations Action
```

### 2. OutputFormatter (`src/outputs/formatter.ts`)

**Purpose**: Formats operation results as GitHub Actions outputs (string key-value pairs)

**Responsibilities**:
- Convert operation results to standardized string outputs
- Ensure all outputs match `action.yml` schema
- Validate outputs using Zod schemas
- Provide machine-readable output for workflow automation

**Output Destination**:
- GitHub Actions outputs (accessed via `${{ steps.sst.outputs.* }}`)
- String key-value pairs only (GitHub Actions requirement)

**Key Methods**:
```typescript
class OutputFormatter {
  formatOperationForGitHubActions(result: OperationResult): ValidatedOutputs
  validateOutputs(outputs: Record<string, string>): ValidatedOutputs

  // Operation-specific formatters
  private formatDeployOperation(result: DeployResult): DeployOutputs
  private formatDiffOperation(result: DiffResult): DiffOutputs
  private formatRemoveOperation(result: RemoveResult): RemoveOutputs
  private formatStageOperation(result: StageResult): StageOutputs
}
```

**Example Output** (GitHub Actions outputs):
```yaml
success: "true"
operation: "deploy"
stage: "production"
completion_status: "complete"
app: "my-sst-app"
resource_changes: "5"
outputs: '[{"key":"ApiUrl","value":"https://api.example.com"}]'
resources: '[{"type":"AWS::Lambda::Function","name":"my-function","status":"created"}]'
# ... all other output fields as strings
```

## Key Differences

| Aspect | OutputFormatter | OperationFormatter |
|--------|----------------|-------------------|
| **Purpose** | Machine-readable outputs | Human-readable content |
| **Output Format** | String key-value pairs | Markdown with formatting |
| **Validation** | Strict Zod schema | Visual consistency |
| **Consumer** | GitHub Actions workflows | Developers reading comments |
| **Required** | Yes (always runs) | Conditional (based on settings) |
| **Content** | All fields as strings | Selected fields with formatting |

## Data Flow

### 1. Operation Execution → Output Formatter

```typescript
// In main.ts
const result = await executeOperation(operation, options);
const outputs = OutputFormatter.formatOperationForGitHubActions(result);

// Sets GitHub Actions outputs
for (const [key, value] of Object.entries(outputs)) {
  core.setOutput(key, value);
}
```

### 2. Operation Execution → Operation Formatter

```typescript
// In GitHubClient
const formatter = new OperationFormatter(config);

// For PR comments
const comment = formatter.formatOperationComment(result);
await this.createOrUpdateComment(comment);

// For workflow summaries
const summary = formatter.formatOperationSummary(result);
await core.summary.addRaw(summary).write();
```

## Design Rationale

### Why Two Formatters?

1. **Separation of Concerns**: Machine-readable vs human-readable output are fundamentally different requirements

2. **Different Consumers**:
   - Workflows need structured data for automation
   - Developers need readable summaries for understanding

3. **Different Validation**:
   - Outputs must match exact schema from `action.yml`
   - Comments need visual appeal but flexible structure

4. **Different Lifecycles**:
   - Outputs always run and are critical
   - GitHub integration is optional and non-critical

### Alternative Architectures Considered

#### Option A: Single Unified Formatter (Rejected)
```typescript
class UnifiedFormatter {
  format(result: OperationResult, type: 'outputs' | 'comment' | 'summary'): string
}
```
**Rejected because**: Mixes concerns, harder to test, violates single responsibility

#### Option B: Per-Operation Formatters (Future Consideration)
```typescript
class DeployFormatter {
  formatOutputs(result: DeployResult): DeployOutputs
  formatComment(result: DeployResult): string
  formatSummary(result: DeployResult): string
}
```
**Consideration**: Could simplify code by grouping all deploy-related formatting
**Trade-off**: More files, but better organization for large codebases

## Usage Guidelines

### When to Use OutputFormatter

Use `OutputFormatter` when you need to:
- ✅ Set GitHub Actions outputs
- ✅ Provide data for workflow automation
- ✅ Ensure schema compliance with `action.yml`
- ✅ Convert operation results to strings

### When to Use OperationFormatter

Use `OperationFormatter` when you need to:
- ✅ Create PR comments
- ✅ Generate workflow summaries
- ✅ Format human-readable content
- ✅ Add visual elements (emojis, badges, markdown)

## Configuration

### OperationFormatter Configuration

```typescript
interface FormatConfig {
  includeTimestamp: boolean;     // Add timestamps to output
  includeDuration: boolean;      // Show operation duration
  includeDebugInfo: boolean;     // Include debug information
  maxUrlsToShow: number;         // Limit URLs in output
  maxResourcesToShow: number;    // Limit resources displayed
}

const formatter = new OperationFormatter({
  includeTimestamp: true,
  includeDuration: true,
  includeDebugInfo: false,
  maxUrlsToShow: 10,
  maxResourcesToShow: 20,
});
```

### OutputFormatter (No Configuration)

OutputFormatter has no configuration as it must strictly adhere to the `action.yml` schema.

## Testing Strategy

### OutputFormatter Tests

Focus on:
- ✅ Schema compliance validation
- ✅ Field type correctness (all strings)
- ✅ Required vs optional fields
- ✅ JSON field parsing
- ✅ Edge cases (empty values, special characters)

Example:
```typescript
test('formats deploy outputs correctly', () => {
  const result: DeployResult = { /* ... */ };
  const outputs = OutputFormatter.formatOperationForGitHubActions(result);

  expect(outputs.success).toBe('true');
  expect(outputs.operation).toBe('deploy');
  expect(outputs.resource_changes).toMatch(/^\d+$/);
  expect(() => JSON.parse(outputs.resources)).not.toThrow();
});
```

### OperationFormatter Tests

Focus on:
- ✅ Markdown formatting correctness
- ✅ Visual consistency
- ✅ Operation-specific content
- ✅ Snapshot testing for regressions
- ✅ Link formatting

Example:
```typescript
test('formats deploy comment correctly', () => {
  const result: DeployResult = { /* ... */ };
  const comment = formatter.formatOperationComment(result);

  expect(comment).toContain('## ✅ Deploy Success');
  expect(comment).toContain('production');
  expect(comment).toMatchSnapshot();
});
```

## Maintenance Guidelines

### When Adding New Operations

1. Add output formatting in `OutputFormatter`:
   ```typescript
   private formatNewOperation(result: NewResult): NewOutputs {
     // Format all fields as strings
   }
   ```

2. Add GitHub formatting in `OperationFormatter`:
   ```typescript
   private formatNewComment(result: NewResult): string {
     // Format markdown for PR comments
   }

   private formatNewSummary(result: NewResult): string {
     // Format markdown for workflow summaries
   }
   ```

3. Update `action.yml` with new output fields

4. Update `src/outputs/schema.ts` with validation

### When Modifying Outputs

1. Update `action.yml` first
2. Update `src/outputs/schema.ts` validation
3. Update `OutputFormatter` formatting logic
4. Run validation tests
5. Update documentation

### When Changing Display Format

1. Modify `OperationFormatter` only
2. Test with snapshot tests
3. Update examples in documentation

## Questions & Answers

**Q: Why not merge the formatters?**
A: They serve different purposes - one for machines (structured data), one for humans (readable content). Merging would violate single responsibility principle.

**Q: Can I use OperationFormatter output in workflows?**
A: No, use OutputFormatter. OperationFormatter produces markdown meant for display, not parsing.

**Q: Why are all OutputFormatter outputs strings?**
A: GitHub Actions requires all outputs to be strings. We use Zod to ensure type safety while maintaining string format.

**Q: How do I add a new field to outputs?**
A: Update `action.yml`, add to `GitHubActionsOutputSchema`, update formatters, and add tests.

**Q: Which formatter runs first?**
A: OutputFormatter always runs first (in main.ts) because it's critical. GitHub integration runs after, even if it fails.

## Summary

The dual-formatter architecture provides:
- ✅ Clear separation between machine and human output
- ✅ Type-safe validation for workflow automation
- ✅ Flexible, rich formatting for developers
- ✅ Independent evolution of each formatter
- ✅ Robust error handling (GitHub integration failure doesn't break outputs)

This architecture follows the **Single Responsibility Principle** and makes the codebase more maintainable and testable.
